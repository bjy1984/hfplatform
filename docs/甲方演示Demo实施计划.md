## 1 结论与本次目标

建议在 hfplatform 建立独立的演示前端，以现有四张 UI 图统一视觉，以 qbms 的命题与题库业务、examsystem 的考务与考试业务作为技术参考。第一阶段使用合成数据和可替换 Mock 服务，完成可操作、可追溯、可重置的业务闭环。业务状态、组卷校验、判分和统计应实际计算，外部接口与设备能力模拟。

推荐演示主线：管理人员发布命题计划 → 专家命题 → 初审退回修改 → 初审、复审、终审 → 入库 → 1+X+Y 组卷与 AB 卷校验 → 配发场次 → 考生作答、刷新恢复与交卷 → 双评及差值仲裁 → 成绩发布、模拟回传与档案查询。另以一份技能题展示准备材料、评分表和现场评分。

首版要使甲方能够判断流程、字段、角色分工和交互是否符合工作习惯，并形成下一轮需求确认记录。它不代表协议中的全部交付及生产验收完成。

“实时计划”在本文件中指随开发证据持续更新的滚动计划：每完成一个任务，更新状态、证据、下一步和偏差。本次以开发完成后的实测结果更新，没有设置定时任务。

## 4 技术实施方案

### 4.1 首版选型

建议采用 Vue 3 + TypeScript + Vite + Vue Router + Pinia + Element Plus + ECharts。这些是参考项目已体现的技术方向；具体版本在 D1 完成依赖兼容和构建验证后锁定，不直接混用两库的版本或多个 UI 系统。

Mock 服务采用浏览器内异步适配器，IndexedDB 保存合成业务状态，页面只调用领域 API。Pinia 管理会话与显示状态，不作为所有数据的唯一持久存储。第一版不要求真实 Java 服务、数据库、Redis 或工作流引擎启动。若需 HTTP 级故障联调，在同一契约下追加本地 Mock Server，不改变页面。

```text
apps/demo-web/src/
  layouts/                 四入口外壳与共享视觉
  features/                workbench / authoring / bank / paper / exam / review / skill / archive
  api/                     页面调用接口及 mock/http 适配器选择
  domain/                  题型、状态机、组卷、核分与校验
  mocks/                   固定种子、场景、故障开关、IndexedDB 仓储
  components/              表格、筛选、状态、步骤、审核轨迹、评分表
packages/contracts/        DTO、枚举、接口请求响应、错误码
docs/                      本计划、源码依据、任务与演示记录
```

以上是拟建目录，尚未创建应用。使用明确的 `mock`/`http` 模式选择；当前只开放 Mock 模式。页面不直接 import 种子文件，后续切换接口时保留页面与状态规则测试。

正式工程继续评估 Java/Spring 领域服务，在理论开发、技能开发、题库组卷、考试、阅卷、集成之间保持边界。一个 Demo 前端不等于已实现协议 2.1.1 的独立部署；正式阶段须单独提供理论/技能部署与协同验证证据。

### 4.2 统一数据模型

| 对象 | 必需字段/关系 | 设计目的 |
| --- | --- | --- |
| Organization / Person / Role | 内部 ID、来源 ID、组织、角色、授权范围 | Mock 与真实组织映射分离 |
| Profession / Level / Subject / KnowledgePoint | 编码、父子关系、启用状态 | 同一知识结构供命题、组卷、分析使用 |
| Bank / BankQuestion | 母库/子库/通用库、组织、questionId | 跨库引用同题，不复制出新的逻辑题号 |
| Question / QuestionVersion | 稳定题号、版本、题型、题干、选项 ID、答案、评分标准、状态 | 修改不污染历史试卷 |
| Plan / Task / ReviewAction | 计划、专家、阶段、提交版本、意见、操作时间 | 三审和退回可追溯 |
| Paper / PaperVersion | 规则版本、种子、题目版本快照、分值、校验结果 | 配卷后固定题面与评分依据 |
| ExamSession / Candidate / Attempt | 场次、人员、卷版本、开始/截止、状态、乱序映射 | 考务和考试共用关联键 |
| Answer / SaveReceipt | attemptId、questionId、序号、请求 ID、保存状态 | 识别迟到保存、重试与交卷状态 |
| MarkTask / ScoreVersion / Arbitration | 匿名号、评分人、逐项分数、阈值、仲裁理由 | 分差处置与成绩版本一致 |
| Archive / IntegrationRecord / AuditEvent | 业务对象 ID、版本、回执、动作、时间 | 档案、接口、统计由同一业务记录派生 |

评分答案留在 Mock 仓储中，考生 DTO 去除标准答案和解析。但纯浏览器 Demo 的数据仍可被开发者工具读取，不能承载真实保密题目；生产必须由服务端鉴权及隔离答案。

### 4.3 Mock 也要遵守的状态规则

- 命题：草稿 → 待初审 → 待复审 → 待终审 → 待入库 → 已入库。演示默认退回命题人，修改生成新版本并重新初审；此退回规则待业务确认。
- 试卷：草稿 → 校验通过 → 冻结 → 配发。冻结后换题形成新版本；不改变已配发/已作答卷。
- 答卷：未开始 → 在考 → 已交卷 → 待评/待仲裁 → 已核定 → 已发布。重复提交返回同一提交结果。
- 成绩：纯客观卷可显示已判结果；有人工题时显示“客观部分已判、最终成绩待核定”。没有完成仲裁不得发布最终分。
- 接口：待发送 → 发送中 → 成功/失败 → 重试成功。同一场次、考生、成绩版本使用同一幂等键。
- 所有写入经业务服务校验当前角色、版本和状态；修改后统一刷新计数。Mock 越权测试验证业务意图，正式服务端仍需重新验证。

### 4.4 核心接口契约示意

| 命令 | 输入 | 输出/失败 |
| --- | --- | --- |
| submitQuestion | 题号、版本、任务 ID、请求 ID | 新状态；版本冲突或任务无权操作 |
| reviewQuestion | 阶段、通过/退回、意见、预期版本 | 轨迹；跳级审核拒绝 |
| generatePaper | 规则版本、候选库、种子、卷数 | 试卷及校验报告；按维度给出短缺 |
| saveAnswer | 答卷、题目、答案、clientSeq、requestId | 本地 Mock 保存回执；旧序号不覆盖新答案 |
| submitAttempt | 答卷、requestId、签字示例 | 唯一提交记录；未到可交卷时间拒绝 |
| submitMark | 评分任务、逐项分数、版本 | 待另一评/待仲裁/已核定；超分拒绝 |
| retryIntegration | 记录 ID、原幂等键 | 同一版本回执，不新增重复成绩 |

时间采用可注入的 DemoClock，默认按场次开始时点计时。迟到“超过30分钟”与开考“15分钟内禁止交卷”保留协议规则；演示员通过“跳到开考16分钟”推进时间并显示演示标识，避免现场等待或偷偷改成15秒。

## 5 合成数据与可复现演示

### 5.1 首批种子

建议一套固定 `scenario-v1`：1 个模拟集团、2 家模拟单位、2 个工种、2 个等级、4 个科目、12 个知识点、8 名模拟专家、30 名模拟考生、3 类题库。所有名称标注“演示”，不使用真实身份、照片、试题或成绩。

准备 120 道可组卷理论题（60 单选、30 多选、30 判断），集中保证一个主演示工种等级的候选量；另准备 6 道技能题，覆盖步骤与评分表。工作草稿、相似题和待审版本单独记录，不混入可组卷候选数。主流程现场新建题在三审入库后成为可选题。

组卷标准样例：A/B 每套 20 题、100 分，10 单选×4 分＋5 多选×8 分＋5 判断×4 分；库来源 50%/30%/20% 按题数为10/6/4。样本生成器须保证各条件交叉分组也有库存，不仅总量足够。AB 示例重复率按共享稳定题号数÷较短卷题数，阈值20%；公式和阈值明确标为演示假设，待 F-17 确认。

理论主观评分用另一个含评分表的合成答卷场景演示，避免把纯客观试卷临时变成混合卷。主观题满分30，双评分18和26，差值8大于演示阈值5，触发仲裁；仲裁22分，客观部分56分，最终78分。技能表20＋30＋50＝100分，示例18＋26＋44＝88分；理论与技能先分列，不擅自加权成认定总成绩。

### 5.2 场景控制

提供“从头演示”“待审核”“待组卷”“考试进行中”“待仲裁”“成绩发布”六个场景快照，可一键重置并明确提示会清除当前演示改动。固定种子和业务时钟使彩排可复现；重置只作用于该应用的 Mock 数据库。

故障开关至少包含：组卷缺题、保存失败、迟到、接口首次失败。监考人数取自同一场次记录；历史统计可以预置，但必须标为合成历史，不能与现场操作计数冲突。

多标签角色演示限定同一浏览器、同一 origin，通过 BroadcastChannel 或版本刷新读取同一 IndexedDB。手机/另一台电脑不会自动共享浏览器存储；首版移动评分用窄屏视图演示，若要求真多设备联动，另增加本地 Mock Server 排期。

### 5.3 约20分钟的甲方演示脚本

| 时间 | 操作 | 甲方核对点 |
| --- | --- | --- |
| 0～2分钟 | 管理工作台查看任务和场次，说明全为模拟数据 | 四角色入口、系统边界、统一待办 |

## 6 15个工作日的滚动实施基线

估算前提：2 名熟悉 Vue 的开发可持续投入，产品/业务评审与测试支持能及时参与；同一浏览器演示；D0为目标，D1仅窄样例；授权组件可用。日期及实际人数尚未收到确认，使用 D1～D15 相对工作日，未按节假日给出承诺日期。两名开发是本次原型估算，不替代协议7.1的正式驻厂团队要求。

预计总开发容量30人日，其中功能建设24人日、联调和彩排修复6人日。若单人开发，建议预留约25～30工作日；3人可在依赖允许的范围内缩短，但不保证线性加速。

## 8 Demo通过条件

1. 固定种子从计划到成绩档案可走通；角色切换后任务和统计同步；无死链或只有“成功”提示而无数据变化的主操作。
2. 新题必须完成三审才进入组卷候选；修订不改变旧卷；跨库同题按稳定ID去重。
3. A/B卷100分、20题、来源10/6/4；校验报告独立重算；缺题或重复率超限明确失败。
4. 多选使用稳定选项ID；刷新后题序/选项/已保存答案不变；切题时保存响应不得写到另一题。
5. 计时测试覆盖开考14:59/15:00、迟到30:00/30:01；模拟时钟和展示标识一致。此处默认迟到30:00仍允许，30:01拒绝，后续按确认口径调整。
6. 保存失败显示待同步；旧序号不覆盖新答案；重复交卷仅一条结果；交卷后不可改答案。
7. 评分超上限/负分被拒；双评差值恰等于阈值时不仲裁（演示默认“>”）；待评/待仲裁不产生最终成绩。
8. 评分 DTO 不含姓名、证件；技能示例总分88；混合卷示例最终78；理论技能不擅自合成总分。
9. 接口原键重试不重复写入；档案可从成绩定位答卷、评分及卷版本；日志中不输出整份答案底稿。
10. 在约定的现代桌面浏览器验证，重点1280×720投屏与1440×900；评分窄屏检查390像素。演示离线不依赖CDN、在线字体或真实外部接口。
11. 自动化重点测状态机、计分、组卷、保存顺序；端到端覆盖命审到出卷、考试到出分、仲裁到回传三条链。演示前连续两次重置并彩排通过。
